# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

FluidBench is two things in one repo:

1. **A static benchmark website** (plain HTML/CSS/JS, no build step) published on GitHub Pages at https://sp-droid.github.io/FluidBench/. It reads JSON records from `benchmarks/` and `submissions/` at runtime.
2. **A Python package `fluidbench`** (`src/fluidbench/`) that downloads a benchmark dataset, trains a user's model, evaluates it, and writes submission JSON in the exact shape the website consumes.

## Commands

Python env is managed with `uv` (Python >= 3.13; torch comes from the CUDA 13.2 PyTorch index configured in `pyproject.toml`).

```bash
uv sync                                  # install deps into .venv
python -m http.server 8000               # preview the site (serve repo root over HTTP; file:// URLs won't work)
python benchmarks/update.py              # regenerate benchmarks/benchmarks.json after adding/removing a benchmark record
python submissions/update.py             # regenerate submissions/submissions.json after adding/removing a submission
```

There is no test suite, linter, or CI. `tests/` holds notebooks that exercise the package end to end (`1.download.ipynb`, `2.cylinder_Re41_interp.ipynb`) plus minimal example models (`minimal_base.py`, `minimal_models.py`) imported by those notebooks.

## Data model (shared contract between Python and the site)

- `benchmarks/benchmarks.json` — manifest `{"benchmarkIds": [...]}`; each ID maps to `benchmarks/{id}.json` (metadata: `source` URL, `loader`, `problem`, `flowVariables`, `inputScalarNames`, split fractions, etc.). Generated by `benchmarks/update.py`, which treats every `*.json` except `benchmarks.json`/`options.json` as a benchmark.
- `benchmarks/options.json` — per-`problem` (e.g. `"Rollout"`) definitions of error categories and metrics. Each entry has a dotted `path` into a submission's `metrics` object; the leaderboard/compare pages use these paths to pick values. Adding a new metric to the site usually means emitting it in `bench.py` **and** referencing its path here.
- `submissions/submissions.json` — manifest `{"submissionsByBenchmark": {benchmarkId: [submissionIds]}}`, generated by `submissions/update.py` from folder layout.
- `submissions/{benchmarkId}/{id}.json` — lightweight record (config + `metrics` + `artifacts` filenames).
- `submissions/{benchmarkId}/{id}/training-history.json` and `rollout-analysis.json` — heavy artifacts, lazily loaded by the compare page.
- All IDs must match `^[a-z0-9_-]+$` (case-insensitive); this is validated in the update scripts, `bench.py`, and `assets/data.js`.
- A benchmark's optional `geometry` field points to a Gmsh `.geo` file under `assets/meshes/`. `assets/geo.js` parses a subset of .geo (variables, Point/Line/Circle, Curve Loop, Plane Surface, Transfinite Curve/Surface, `out[] = Extrude`, Physical Curve/Surface) and builds transfinite grids; named Physical Surfaces are coloured and listed in the viewer legend; `geometry-viewer.js` (three.js via an importmap from jsDelivr) renders every `[data-geometry-viewer]` element: on the benchmarks page it follows `data-dataset-id`, on the leaderboard (`data-follow-selection`) it follows `#dataset-filter`.
- `.txt` files in `benchmarks/` (e.g. `cylinder-flow.txt`, `wing.txt`) are inactive drafts — intentionally not picked up by the manifest.

## Python package

- `fluidbench.download(id)` → `downloader.download_dataset`: reads `benchmarks/{id}.json` (path resolved relative to the repo, so the package assumes it runs from this checkout), dispatches on `loader` (only `"huggingface"` today), and fetches `train.h5`, `validation.h5`, `test.h5` into `./downloads/{id}/` under the **current working directory**. Add new loaders to `_LOADERS` in `downloader/__init__.py`.
- Split H5 layout: `inputs/scalars`, `inputs/fields`, `targets/fields`, wrapped by `CFDataset` which yields `((scalars, fields), target)`.
- `fluidbench.run(model, config)` in `bench.py`: validates config (`id`, `datasetId`, `model`, `authors`, `year`, `representation` ∈ {Graph, Grid}), builds DataLoaders (batch 8), calls `model.fit(train_loader, val_loader)`, then evaluates the test split (single-step metrics, autoregressive rollout via `model.predict_rollout`, per-variable RMSE, kinetic-energy spectrum) and writes output to `./submission/{datasetId}/` in the CWD. Note: `submission/` (singular, gitignored) is the output; it is copied by hand into `submissions/` (plural, tracked) to publish.
- Duck-typed model interface expected by `run`: `fit(train_loader, val_loader) -> history`, `predict_rollout(loader)`, `total_parameters`, plus device handling — see `tests/minimal_base.py` for the reference implementation.
- `benchmarks/{id}.ipynb` notebooks build the dataset H5 splits and metadata from an external FluidLearn data folder; they are not runnable without that sibling repo.

## Website

- `assets/site.js` must load first: it computes `window.FluidBenchPaths` (site root derived from the script URL) so pages work both at `/` locally and under `/FluidBench/` on GitHub Pages. Always build fetch URLs via `FluidBenchPaths.url(...)`, never hardcoded absolute paths.
- `assets/data.js` is the single data-access layer (cached `readJson`, manifest loading, artifact path validation); page scripts (`leaderboard.js`, `compare.js`, `benchmarks.js`, `models.js`, `top-model.js`, `dataset-tags.js`) consume it.
- Pages live in `pages/`; `index.html` is at the root.
